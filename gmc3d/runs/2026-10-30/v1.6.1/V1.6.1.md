# gmc3d v1.6.1 (30 Oct 2026): every OpenMC input that is not a physics stage

Phani's ask: "make a v1.6.1 implementing all those 18 then recalculate the
gaps of our code and give me the updated one". Done: the 18 items are in,
the gaps list is rewritten (`GAPS.md`), and every new input is checked
against OpenMC 0.16.

## Found and fixed while checking

The first gapcheck runs failed 7 of 18 cases. Each failure was diagnosed
to a cause before anything changed:

1. **MaterialFrom crossing flux 70 sigma off.** OpenMC scores a vacuum
   leak with `material_last`, which no cell search has updated there (the
   material before this cell, or none after a collision). gmc3d used the
   cell's own material. Fixed for vacuum and the first score at a
   reflection.
2. **CellFrom / MaterialFrom crossing tallies in lattices were refused.**
   OpenMC scores every lattice wall crossed (`event_cross_surface`), with
   the normal along the step. Now done the same way (the gap is gone).
3. **Curved-mesh phi faces.** With two phi bins every crossing was filed
   as "going up" (the bin numbers cannot tell the way). The way now comes
   from phi itself.
4. **Curved-mesh inward crossings: OpenMC is wrong.** OpenMC files an
   in-crossing by the next face of that axis along the ray in the element
   entered, not the face crossed (`mesh.cpp`, raytrace_mesh). It reports
   currents in through the r = 0 "face" of the innermost shell, which does
   not exist. gmc3d files them by the face crossed; the check compares
   out-crossings bin by bin and in-crossings summed per element and axis.
5. **Mu filter 9.5 sigma off.** A run in a pure scatterer showed ours
   leaning (flux 1.054 to 0.942 of the mean across 4 mu bins) where OpenMC
   and an independent 30-line analog code were flat. An independent 3D
   check (`mu/sph3.py`; the analog code is `mu/mu_test.py`) reproduced ours exactly for the scattered
   flights, so the difference was the unscattered ones: OpenMC never
   resets the scatter cosine between histories, so it bins a history's
   first flight by the cosine the previous one ended with, which leans
   forward (0.15 / 0.21 / 0.28 / 0.36 in a leaking sphere). gmc3d now
   carries it the same way. Two snags on the way:
   - under implicit capture our histories end by leakage or roulette, not
     absorption, so the carried cosine would be the wrong one; each Mu run
     now follows the analog history its walk stands for (an absorption
     coin per flight with probability 1 - exp(-sigma_a l); roulette waits
     until that history is absorbed, which keeps the weights unbiased);
   - a store into `XS.mu_last` inside `_advance`'s prange body never
     reached `_track` in compiled code (it did with numba off); moved into
     a helper call. After: 1.4273 / 1.4277 / 1.4224 / 1.4246 against
     OpenMC 1.4242 / 1.4262 / 1.4258 / 1.4254.
6. **Periodic albedo current half of OpenMC's**: OpenMC scores it with the
   weight that arrived (wgt_last), before the albedo. Fixed.
7. **Biased isotropic source**: OpenMC 0.16's `Tabular.evaluate` takes one
   value at a time. Fixed.

Also found: OpenMC's `CylindricalMesh` with a phi range of pi/3 in a
rotational wedge sums 6% below its own cell tally of the same region
(ours agrees with ours), so that case uses a RegularMesh.

## Robust

`checks/robust.py` used albedo, collision estimator, fission score and horn
torus as its "must be refused" features; they are all accepted now, so
those models run and must PASS, and the refusal test uses a tally
derivative and the events score instead. First run (`robust_first.log`):
26 PASS, 3 refused cleanly, 0 FAIL, 1 ERROR. The error was model 13:
OpenMC lost particles. Cause: the random builder cut the horn torus out of
its object without giving the hole to the background, so a region was in
no cell. That is the test model's fault, not gmc3d's; fixed in the builder
(model 13 now PASS) and the suite rerun (`robust.log`): 27 PASS, 3 refused
cleanly, 0 FAIL, 0 ERROR. Model 26 failed at 1x and passed at 5x, as in
v1.6.0 (the deep reference bin item in GAPS.md's open checks). Score
after the rerun: 9.9 / 10, random models 30 / 30.

## Speed

Plain MC on old problems, 200k x 4 histories, best of 3, same machine and
session, four passes in alternating order (`speed.log`):

| problem | v1.6.0 | v1.6.1 |
|---|---|---|
| cask | 22.6 s | 24.2 s (+7%) |
| hexcore | 31.8 s | 33.7 s (+6%) |
| curved | 71.1 s | 75.6 s (+6%) |

The answers are bit-identical to v1.6.0. The cause is not the general
scorer's branches in the flight loop: a build with them compiled out ran
the same as v1.6.1. Not found further; it is in GAPS.md's open checks. A
build with `_track` inlined into `_advance` was 2x faster on hexcore but
gave a wrong answer, so it was discarded. Cold-cache compile time also
went from 54 s to 115 s (the general scorer's code compiles even when
unused).

## Limits

- The lattice-wall crossing flux with a rotated lattice is not compared
  with OpenMC (OpenMC mixes frames there, from reading its source).
- Reaction-name scores other than heating and (n,gamma) are assumed to be
  refused by OpenMC in multigroup mode, not each measured.
- The network was checked on point detectors only; the general scorer's
  tallies were checked with the exact walk.
